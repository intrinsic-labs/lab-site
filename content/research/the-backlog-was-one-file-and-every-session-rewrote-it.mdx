Our company's operating record is a folder of Markdown under git — one directory per project, with a brief and a backlog. Until 2026-08-27 that backlog was a single file, `tasks.md`, holding one dense line per task:

```
- [ ] task text  @owner  due:2026-07-10  ~30m  #tags  ^lit-3
```

Compact, diff-friendly, readable on a phone, hand-editable. It worked for about a year. On 2026-08-27 all twelve active projects moved to one file per task, and a thirteenth followed two days later. This is what forced it and what it cost.

## The problem, in two parts

**A single unlocked file that every writer rewrote wholesale.** Autonomous work sessions run concurrently, up to three at a time. Each reads its project's backlog at spawn and rewrites it on the way out to tick its own checkbox and append a completion note — so two sessions in one project are a last-writer-wins race over a file both read minutes apart. The mitigation, shipped a week before the migration, was to make concurrency stop at the project boundary: at most one session per project per tick, unconditional, no kill switch, on the grounds that the state a switch would restore is "two sessions may race the backlog." A real constraint on throughput, bought entirely by a file-layout decision.

**Facts asserted in prose instead of read from the world.** An internal audit that morning named this the system's first disease: the same fact lives in up to five prose locations — code, the repository's agent instructions, the project brief, the backlog, the generated to-do surface — and only writing code updates one of them. It identified 15 duplication pairs. About 70% of the resulting drift was five-minute documentation edits; the dangerous 30% was one class, **"done" asserted in prose while the code sat on an unmerged branch**, with three named instances. The audit's summary: *"the system narrates state instead of reading it."*

There was also a pull, not just a push. From a retrospective conversation four days later: *"having deadlines, milestones, and all these individual open issues has been a huge asset as far as understanding what to work on next... That inspired a big refactor in the [operating record] last week as far as task shape."* The constraint on that impulse was explicit: **take the rigor, not the dependency.** No external tool — a strict grammar and a linter, in files that stay readable from a terminal and from a phone.

## What changed

A task is now `tasks/<id>.md`: YAML front matter, a one-line outcome, then why, acceptance criteria, and an append-only dated discussion. Four properties do the work.

**Location is a fact, not a claim.** `tasks/` holds live work; `tasks/done/` and `tasks/cancelled/` hold the rest. A status change *moves the file*, and the linter treats disagreement between a file's status field and its directory as an error — so the directory is a reliable view of live work rather than a section heading somebody has to maintain.

**Some fields refuse some authors.** Every write to a due date records who made it, and a date stamped as the human's is never machine-overwritten — the setter refuses structurally rather than being asked not to in a prompt. The in-progress status is scheduler-only: stamped at dispatch, cleared at completion, and the setter refuses to set *or clear* it for any other actor, because a model writing "in progress" is the system narrating its own state again. A default due date the store assigns appends a discussion line saying so, so a default never reads like a date somebody stated.

**Every write is proved rather than trusted.** The file is reparsed before and after, and the write is refused unless the named field — plus only its declared derived companions — is what changed. And the layout makes half of it free: **one task per file means a write cannot touch a neighbouring task, because there isn't one.**

**The deferred section became a number.** The old "later" heading is now `rank >= 900`; order within a file carries nothing. Ids are allocated above the maximum of three sources — the new task files, the frozen old file, and a durable high-water record — so an id is never reused across the seam even after the old file is deleted.

## What it cost

The audit document was committed at 15:39 UTC, the store shipped at 17:41, the migrator at 18:12, and all twelve projects were converted by about 01:40 the next morning. That speed is the cost centre.

**194 files needed a corrective sweep.** The migrator's mechanical field mapping wrote every task's "why" section as a verbatim copy of its one-line summary. Four days later a sweep emptied 100 of them and trimmed 94, and a linter rule was added so the shape cannot quietly return.

**The independent review gate went blind for a day.** Every code-producing session ends by having a fresh session review its diff against the task's acceptance criteria. That path held a hardcoded path to the old file and was never rewired — so any task created after its project migrated resolved to nothing, and **the reviewer reviewed a diff with no acceptance bar at all**, silently. A task that cannot be resolved now fails the review outright instead of proceeding with an empty standard.

**Two tasks were each dispatched twice in one day.** Clearing the in-progress status returned a task to open, which is correct for a crash and wrong for a session that concluded the task's premise was already satisfied. The repair added a terminal "contested" status — a task flagged as disputed, held out of scheduling until a human looks at it.

**CI went red twice** from a test asserting the legacy corpus was non-empty — permanently false after the migration. The fix is worth recording: keep the legacy path covered by a synthetic fixture and skip only the live-corpus assertion, because "a guard that skips to nothing proves nothing." And **the agent instructions documented only the dead format** for about a day, so any agent reading them cold would hand-edit a frozen file and lose the write.

## What is still open

The linter exists, has 24 rules, and **is not wired into CI**. The migrator invokes it; nothing else does automatically. Running it today gives 45 findings, no errors. Thirty are discussion entries over the 300-character limit — a limit the documentation calls hard-rejected and which the store's append path does enforce. Thirty violations therefore mean thirty entries written by something that bypassed the store, which is precisely the failure mode the design exists to remove.

**Zero epics and zero milestones exist.** The schema supports them, the store has query functions, the linter has dangling-pointer rules, and the documentation describes membership in the present tense. Nothing uses any of it.

**The twelve frozen files are past their deletion window and still on disk.** Seven days after a project's freeze, a report line names the file and what still reads it; that report has fired for all twelve. It is deliberately report-only, because the frozen file is the only working-tree copy of that project's pre-migration completed-task history — the migrator never carried those records across. So the migration is, by its own definition, unfinished, and the thing that surfaces it correctly refuses to finish it.

**The concurrency ceiling still stands on a premise that no longer exists.** At most one session per project per tick, unconditional, no kill switch — because the backlog is "a single unlocked file every session rewrites." It isn't any more; the store's own comment says the cross-task half of that safety is now structural. The measurement that would settle it has not been run: lift the cap in one project, run two concurrent sessions, and check whether any write outside the two task files under edit occurs. Until then it is a limit we pay for out of habit.

There is **no decision-log entry** for the largest data-model change of the month, in a record whose append-only decision log is supposed to hold exactly that. And there is **no transcript** of the conversation that decided it — the deciding session survives only as a third-person findings summary, which is the failure mode the company's own three-day-old "keep transcripts, not summaries" rule was written to prevent.

## Where this goes next

Three have clear finish lines. Wire the linter into CI and the thirty over-length entries become a build failure rather than a standing report, which also names whatever still writes around the store. Carry the pre-migration completed-task records across and the twelve frozen files can be deleted, which is what finishes the migration. And the concurrency ceiling has a one-afternoon experiment attached: lift it in one project, run two sessions at once, and check whether any write lands outside the two task files. If none does, the cap comes off and the throughput it costs comes back. If one does, the structural claim this post rests on is wrong — worth more than the throughput.
