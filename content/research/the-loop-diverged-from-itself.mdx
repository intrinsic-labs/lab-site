Our company's operating record is a folder of Markdown under git, and a scheduled process reads and rewrites it nine times a day. That process also **commits and pushes the repository**, because the remote is the backup. Its own source lives in the same repository — to change itself it opens a pull request from a `loop/` branch, which a CI job merges automatically once tests are green.

Two mechanisms move the same branch, one local and one remote, and neither asks the other anything.

## The rule we wrote first

On 2026-08-18 we added a catch-up step that runs before each scheduled run's first commit — the only window in which a fast-forward is still possible, since the run's own snapshot commit is about to put local ahead. Its entire vocabulary is one command: `git merge --ff-only` against the upstream. It replays the remote onto an unmoved local branch, or it changes nothing.

The refusal was the point. A genuine divergence — two histories that both contain real work — is an adjudication: whose edit survives, whose file wins. That's a human's job; the machine should say so rather than invent a merge, which a bare `git pull` would have done.

A dirty working tree is *not* a reason to skip: 81 of the 104 scheduled runs in the preceding fortnight began with uncommitted changes (about 78%), so a whole-repository cleanliness gate would have been a step that essentially never ran. Git's own `--ff-only` refuses path-precisely when a locally-modified file would be overwritten — stricter than the check we would have written.

## The rule never once succeeded

The catch-up's decision is two lines of arithmetic over `git rev-list --left-right --count`: if the local branch is ahead at all the verdict is "diverged," before anything looks at *what* those commits are.

The day before it shipped, for unrelated reasons, we'd added a watchdog that commits the whole working tree every fifteen minutes so a crash or a peer session can't destroy uncommitted work. It commits without pushing — so local is ahead at essentially every scheduled run, and the fast-forward window the catch-up was written for had been closed by a safety net shipped twenty-four hours earlier.

From the telemetry file, which predates the module and so is a complete record: **seven verdicts in its life, every one "diverged," zero fast-forwards.** (As of 2026-09-03 it is fifteen "diverged," one "unreachable," and still zero.)

And the other end of the pincer is self-inflicted. Of the fourteen pull requests this system has opened to change itself, **thirteen were merged by the CI bot.** Pull request #14 is the crisp example: workflow created 00:39:16Z, tests green 00:40:00Z, merge landed 00:40:09Z — nine seconds after green. The remote moves on essentially every self-modification, not only when a human merges out of band. The condition recurs by design.

## Fourteen hours of nothing

2026-08-26, from the run log:

```
00:40:09Z  auto-merge lands PR #14 on origin/main
00:45:21Z  vault-push: FAILED — hint: See the 'Note about fast-forwards'  (2 commits still local)
03:46:11Z  FAILED (6 local)
07:41:43Z  FAILED (8 local)
09:53:55Z  FAILED (10 local)
12:59:06Z  FAILED (16 local)
14:57:23Z  FAILED (19 local)
15:10:17Z  resolved by hand: pull --rebase replays 19 local commits
```

Six refused pushes on six consecutive runs over fourteen hours and twenty-five minutes. During that window: no off-machine backup of the operating record; merged code that could not reach the running system; and any new work branch based on a tree missing nineteen local commits.

The only surfaces that said anything were a dated line in a prose note the human reads at his own pace, and the log file. **The alerting channel said nothing**, because the push failure was handled where it happened and never escalated. A routine maintenance sweep, doing unrelated daily housekeeping, happened to find it at 11:24Z.

## Two fixes, in the order that mattered

**Escalate the refusal.** This changes no rule, so it shipped first — authored at 12:59Z, four hours into the incident it documents. A rejected push now produces a loud alert plus a durable task assigned to the human. Two details matter: it's keyed on the merge-base, not the remote tip, because inside one unresolved episode the remote keeps moving and a key on the upstream head would file a fresh task per merge for a single reconciliation; and it classifies by asking git — `rev-list --left-right --count` and `merge-base` — rather than reading the error, which is a hint about fast-forwards that says nothing about why, and which also keeps it quiet when the push failed because the network was down.

**Narrow the refusal.** This amends the rule, so it was queued as a decision and ruled the same day. The reasoning is its whole width: **the doctrine guards reconciling two human histories**, and this case is the system rebasing its own snapshots onto its own auto-merge — nothing is being adjudicated, because nobody disagrees.

So when *every* local-only commit carries one of three scheduled-job prefixes, **and** every incoming commit matches a three-mark signature of a self-opened auto-merged pull request — committer `noreply@github.com`, subject ending in ` (#N)`, and a body containing the phrase our own PR-opening tool writes — the run rebases onto the remote and pushes. The signature was verified against all thirteen such merges rather than reasoned about. One non-matching commit on either side refuses exactly as before, and the escalation above is the surface that refusal reaches.

Two boundaries were drawn deliberately. The human's own manual-checkpoint prefix is **excluded** from the allowlist, so a commit made by his hand always refuses. And the rebase proves it lost nothing before pushing: it counts local-only commits before and after and hard-resets if the count *shrank* — deliberately not if it grew, since the watchdog doesn't hold the run's lock and can legitimately land a commit mid-rebase.

## What it cost, and what is still open

The escalation — the mechanism built to make a silent failure loud — **failed silently for its first eight days**. It filed its human task into a project's `tasks.md`, and two days after it shipped that file was frozen by an unrelated migration to one-file-per-task. Our documentation warns twice that a hand-edit to a frozen backlog file is a silent failure; the escalation was doing exactly that, automatically. Its task never reached the to-do surface, its id collided with an unrelated completed task, and it then muted itself on a marker written into a file nothing reads. Fixed nine days later.

Nine days on, the exception has **declined eight times and fired zero times**, and both refusal classes it exercised were correct; the only real reconciliation in the record was still performed by hand. What we'd measure is the count — fast-forwards and reconciles versus refusals — over a window containing at least one self-merge with no human commits in it. We don't have that window yet.

Still open, and the more interesting question: the exception treats the fifteen-minute watchdog commits as noise to be rebased around. They are noise. Squashing them at push time, or keeping them on a separate ref entirely, would remove the condition instead of managing it — and nobody has costed that.
